# 生成测试用例

一条好的测试用例通过外部可观察结果验证一个由 Spec 定义的行为，并能区分符合 Spec 的实现与可信的错误实现。

## 需求依据

完整阅读 Spec 和 [testcases.md](testcases.md)。以 Spec 为预期行为的唯一依据，不读取实现代码，也不虚构产品行为。

参考示例中好用例的特征，避免坏用例所展示的问题。示例只说明用例的质量标准，用户提供的测试数据只用于准备或选择数据，二者都不能定义预期行为。

## 设计并生成

根据 Spec 中的行为选择合适的黑盒测试设计方法。可一次处理整份 Spec，也可分轮处理，并根据需要按相关行为分组。设计过程中，在内部将范围内可确定的 Spec 规则映射到用例、数据行或澄清问题。

## 质量标准

- 对每项预期结果，设想一种违反对应 Spec 规则的可信错误实现。只有本用例能观察到不同结果时才保留该断言，否则改进测试数据、操作或观察方式。
- 合并实质重复的内容时，保持规则覆盖完整、失败可独立诊断。
- 返回前，依据 Spec、本 Skill 和 `testcases.md` 检查统一用例集的覆盖和质量。
- 根据复核报告修订时，一次处理全部有 Spec 或本 Skill 依据的生成缺陷，保持未涉及内容不变。
- 依据 Spec 和用例证据处理重复问题及复核分歧；现有依据不足以裁决，或修订持续无法取得进展时，向用户说明并请求决定。

## 信息缺失

若因需求不明确、需求冲突或测试能力不足而无法形成确定且可执行的用例，应向用户提问并省略受影响的用例，不得虚构或将其标记为阻塞。

继续生成未受影响的用例。只有该问题导致其余用例也无法可靠生成时，才停止整份用例集。
