# 生成测试用例

一条好的测试用例通过外部可观察结果验证一个由 Spec 定义的行为，并能区分符合 Spec 的实现与可信的错误实现。

## 需求依据

完整阅读 Spec 和 [testcases.md](testcases.md)。遵循其中好用例的特征，避免坏用例的模式。示例只定义用例质量，不定义产品行为。Spec 是预期行为的唯一依据，用户提供的测试数据只用于准备或选择测试数据，不能定义预期行为。不要读取实现代码，也不要虚构产品行为。

## 设计并生成

根据需要一次或分多轮处理 Spec，并可按相关行为分组。在内部将范围内的每项规则，以及 Spec 明确列出的每个角色、取值、字段、运算符、状态、输出和失败情况，映射到一条用例或独立数据行。按需选择适用的黑盒测试设计方法。

## 质量标准

- 对每项预期结果，设想一种违反对应 Spec 规则的可信错误实现。只有本用例能观察到不同结果时才保留该断言，否则改进测试数据、操作或观察方式。
- 只合并实质重复的内容，并且只能在完成覆盖映射后合并。
- 返回统一用例集前，检查完整 Spec 的覆盖情况，并依据 Spec、本 Skill 和 `testcases.md` 逐条检查每条用例及数据行。不合格的内容应修复或省略，并对每项因信息或测试能力不足而省略的内容向用户提问。

## 信息缺失

当未知或相互冲突的需求，或者测试能力不足，导致无法形成确定且可执行的用例时，应向用户提问并省略受影响用例，不得虚构，也不得将其标记为阻塞。继续生成未受影响的用例；只有该问题导致其余用例也无法可靠生成时，才停止整份用例集。
