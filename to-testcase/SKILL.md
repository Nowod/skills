# 生成测试用例

生成有需求依据、可供人工执行的黑盒测试用例，通过外部可观察结果区分符合 Spec 的行为与实际可能出现的错误行为。

## 需求依据

以 Spec 中的产品行为要求确定预期结果。仅说明范围、现状或测试限制的内容用于确定覆盖范围或识别缺口。

结合用户提供或项目指定的测试数据设计执行对象、前置条件和输入。按照 [testcases.md](testcases.md) 中的用例约定编写用例，参考其中的示例判断质量。

不读取实现代码，也不以测试数据或示例补充产品行为要求。

## 理解需求

阅读当前任务范围内的 Spec，理解主要行为、共同规则和相互依赖，明确需要覆盖的范围。

## 设计并逐条整理

结合相关 Spec 原文、可用测试数据及必要的关联信息，选择合适的黑盒测试设计方法，用独立用例覆盖范围内可确定的规则。

结合行为交互和实际可能出现的错误设计场景、数据及必要的组合，使预期结果能够通过对应操作后的外部观察加以判断。合并实质重复的内容时，保持覆盖完整、失败可独立诊断。

从执行者视角逐条整理用例，使执行者仅凭该用例，就能理解测试目的、准备所需数据或文件、建立前置条件、完成操作并判断结果。

## 整体核对

逐条整理完成后，回到 Spec 核对用例集的覆盖和预期结果，检查是否存在遗漏或偏差、共同规则的应用是否一致、相关行为之间的关联是否得到覆盖。

修订发现的问题后，输出用例集，并说明尚未解决的缺口及其影响范围。

## 信息缺失

利用 Spec 和可用测试数据仍无法形成确定且可执行的用例时，向用户提出具体问题，说明缺口及受影响范围。省略受影响的用例，不虚构内容或生成标记为“阻塞”的占位用例。

继续完成未受影响的部分；只有缺口使其余用例也无法可靠生成时，才暂停整个任务。

## 复核修订

结合 Spec、本 Skill 的用例要求和用例证据判断复核意见，修正成立的问题及其必要的关联影响，避免无关改动。

现有依据不足以解决分歧，或修订反复而没有进展时，说明未解决的问题及原因，请用户决定。
