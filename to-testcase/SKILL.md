# 生成测试用例

一条好的测试用例通过外部可观察结果验证一个由 Spec 定义的行为，并能区分符合 Spec 的行为与可信的错误行为。

## 需求依据

完整阅读 Spec 及相关澄清，只将其中明确规定的产品行为作为预期依据，不读取实现代码，也不虚构产品行为。仅说明范围、现状或测试限制的内容用于确定用例范围或识别缺口，不转化为预期结果。

参考 [testcases.md](testcases.md) 中好用例的特征，避免坏用例所展示的问题。

用户提供或项目指定的测试数据可用于准备或选择数据，以及确定实际执行对象，但不能定义预期行为。

## 初步设计

根据 Spec 中的行为选择合适的黑盒测试设计方法。可一次处理整份 Spec，也可分轮处理，并根据需要按相关行为分组。

设计时，确保范围内可确定的 Spec 规则均由用例或数据行覆盖。

对每项预期结果，设想一种违反对应 Spec 规则且实际可能出现的错误行为。只有用例能够观察到正确行为与该错误行为的差异时，才保留该断言；否则改进测试数据、操作或观察方式。

合并实质重复的内容时，保持规则覆盖完整、失败可独立诊断。

## 复核修订

根据复核报告修订时，一次处理全部有 Spec 或本 Skill 依据的生成缺陷，保持未涉及内容不变。

依据 Spec 和用例证据处理重复问题及复核分歧；现有依据不足以裁决，或修订持续无法取得进展时，向用户说明并请求决定。

## 逐条整理

形成当前用例集后，从执行者视角逐条整理用例。审视每条用例时，确保执行者仅凭该用例及其引用的必要测试数据，就能确定前置条件、操作和预期结果。

逐条整理完成后，回到整体视角核对 Spec 规则与用例集，确认整理没有造成覆盖遗漏或改变预期行为，再输出结果。

## 信息缺失

若因需求不明确、需求冲突、缺少必要的测试数据或测试能力不足而无法形成确定且可执行的用例，应向用户提问并省略受影响的用例，不得虚构或将其标记为阻塞。

只有该问题导致其余用例也无法可靠生成时，才停止整份用例集。
